### 🧱 TP 2 – Construction d’image Docker personnalisée
🎯 Objectif

Créer ta propre image Docker au lieu de modifier un conteneur à la main.

1️⃣ Préparer le projet
📁 Créer le dossier du projet
```
mkdir tp2-docker
cd tp2-docker
```

📄 Créer le fichier HTML
```
nano index.html
```

👉 Contenu version 1.0 :
```
<!DOCTYPE html>
<html>
<head>
    <title>Mon site Docker</title>
</head>
<body>
    <h1>Mon site - Version 1.0</h1>
</body>
</html>
```

➡️ Sauvegarder : Ctrl + O → Entrée
➡️ Quitter : Ctrl + X


2️⃣ Écrire le Dockerfile
📄 Créer le Dockerfile

⚠️ Sans extension
```
nano Dockerfile
```
📦 Contenu du Dockerfile
```
FROM nginx:alpine

COPY index.html /usr/share/nginx/html/index.html

EXPOSE 80
```
🧠 Explication

FROM nginx:alpine → image légère

COPY → ajoute ton fichier HTML dans Nginx

EXPOSE 80 → documente le port utilisé


3️⃣ Construire l’image
🔨 Build de l’image (version 1)
```
sudo docker build -t mon-site:v1 .
```

👉 Tu verras :

téléchargement de l’image de base

étapes (layers) FROM, COPY, EXPOSE

🔍 Vérifier les images
```
sudo docker images
```

4️⃣ Tester l’image
▶️ Lancer un conteneur avec v1
```
sudo docker run -d -p 8081:80 --name site-v1 mon-site:v1
```
🌐 Vérifier dans le navigateur
```
http://localhost:8081
```

👉 Tu dois voir : Mon site – Version 1.0

5️⃣ Itérer (version 2)
✏️ Modifier le HTML
```
nano index.html
```

Remplace par :
```
<h1>Mon site - Version 2.0</h1>
```
🔨 Rebuild avec un nouveau tag
```
sudo docker build -t mon-site:v2 .
```
▶️ Lancer la version 2
```
sudo docker run -d -p 8082:80 --name site-v2 mon-site:v2
```
🌐 Vérification

- Version 1 → http://localhost:8081
- Version 2 → http://localhost:8082

👉 🎉 Les deux versions tournent en même temps

6️⃣ Nettoyer
⏹️ Arrêter les conteneurs
```
sudo docker stop site-v1 site-v2
```
🗑️ Supprimer les conteneurs
```
sudo docker rm site-v1 site-v2
```

🧠 Questions de réflexion (réponses)

Image beaucoup plus légère

Démarrage plus rapide

Moins de surface d’attaque sécurité

### 🐳 TP 3 – Docker Compose : Stack WordPress
1️⃣ Créer le projet
```
mkdir wordpress-compose
cd wordpress-compose
```
2️⃣ Créer le fichier docker-compose.yml

Crée un fichier docker-compose.yml :
```
nano docker-compose.yml
```

Copie-colle ce contenu :
```
version: '3.8'

services:
  wordpress:
    image: wordpress:latest
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_USER: wp_user
      WORDPRESS_DB_PASSWORD: wp_pass
      WORDPRESS_DB_NAME: wordpress_db
    volumes:
      - wordpress_data:/var/www/html
    depends_on:
      - db

  db:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: root_pass
      MYSQL_DATABASE: wordpress_db
      MYSQL_USER: wp_user
      MYSQL_PASSWORD: wp_pass
    volumes:
      - db_data:/var/lib/mysql

  phpmyadmin:
    image: phpmyadmin:latest
    ports:
      - "8081:80"
    environment:
      PMA_HOST: db
      PMA_USER: root
      PMA_PASSWORD: root_pass
    depends_on:
      - db

volumes:
  wordpress_data:
  db_data:
```
3️⃣ Lancer la stack
```
docker-compose up -d
```
Vérifier que tout tourne
```
docker-compose ps
```

Tu dois voir 3 conteneurs : wordpress, db, phpmyadmin.

Voir les logs WordPress
```
docker-compose logs -f wordpress
```
4️⃣ Tester
WordPress

Ouvre dans le navigateur : http://localhost:8080

Termine l’installation (choix de langue, compte admin, etc.)

Crée un article test
```
phpMyAdmin
```
Ouvre : http://localhost:8081

Connecte-toi avec :

User : root

Password : root_pass

Vérifie que la base wordpress_db existe

5️⃣ Vérifier la persistance

Arrêter et supprimer les conteneurs sans les volumes :
```
docker-compose down
```

Relancer :
```
docker-compose up -d
```

✅ Ton article WordPress doit être toujours là, car le volume wordpress_data persiste.

6️⃣ Bonus : Ajouter Nginx comme reverse proxy

Exemple d’ajout dans docker-compose.yml :
```
  nginx:
    image: nginx:latest
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - wordpress
```

Exemple minimal de nginx.conf :
```
server {
    listen 80;
    server_name localhost;

    location / {
        proxy_pass http://wordpress:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```
7️⃣ Questions de réflexion
Question	Réponse courte

- Pourquoi utilise-t-on depends_on ?	
```
Pour que WordPress et phpMyAdmin attendent que la base de données MySQL soit prête avant de démarrer.
```
- Quelle est la différence entre un volume nommé et un bind mount ?
```
Différence entre volume nommé et bind mount	Volume nommé : géré par Docker, persiste même si conteneur supprimé.
Bind mount : répertoire de l’hôte directement monté, utile pour le développement.
```
- Comment les services communiquent-ils ?
```
	Par le nom du service dans le réseau Docker Compose (DNS interne) : db, wordpress, etc.
```

### 🧪 TP 4 – Podman rootless (Niveau Intermédiaire)
🎯 Objectif

Découvrir Podman et son fonctionnement rootless, lancer des conteneurs, utiliser les Pods, et intégrer Podman avec systemd utilisateur.

🟦 1) Installation et vérification de Podman
🔹 Installation de Podman (Ubuntu)
```
sudo apt update
sudo apt install -y podman
```
🔹 Vérification de l’installation
```
podman --version
```

Exemple de résultat :
```
podman version 4.x.x
```
🔹 Vérification de l’utilisation SANS sudo
```
podman info
```

✅ La commande fonctionne sans sudo, ce qui confirme que Podman est utilisable en mode rootless.

🔹 Comparaison avec Docker

Les commandes Podman utilisent la même syntaxe que Docker :

Docker	Podman
docker run	podman run
docker ps	podman ps
docker images	podman images
docker stop	podman stop

👉 Il suffit de remplacer docker par podman.

🟦 2) Premier conteneur rootless (Nginx)
🔹 Lancer un conteneur Nginx (sans sudo)
podman run -d --name nginx-rootless -p 8080:80 nginx


-d : mode détaché
```
-p 8080:80 : port local 8080 → port 80 du conteneur
```
aucun sudo utilisé

🔹 Vérifier que le conteneur tourne
```
podman ps
```
🔹 Tester le fonctionnement
```
curl http://localhost:8080
```

Ou depuis un navigateur :
```
http://localhost:8080
```

✅ La page Nginx s’affiche → conteneur fonctionnel en rootless.

🟦 3) Création et utilisation d’un Pod

Un Pod regroupe plusieurs conteneurs qui partagent le même réseau (localhost), comme dans Kubernetes.

🔹 Création du pod
```
podman pod create --name mon-pod -p 8081:80
```

mon-pod : nom du pod

-p 8081:80 : port exposé pour le pod

🔹 Ajout d’un conteneur Nginx dans le pod
```
podman run -d --name nginx-pod --pod mon-pod nginx
```
🔹 Ajout d’un conteneur Redis dans le même pod
```
podman run -d --name redis-pod --pod mon-pod redis
```
🔹 Vérification des pods et conteneurs
```
podman pod ps

podman ps
```
🔹 Vérification de la communication via localhost

Entrer dans le conteneur Nginx :
```
podman exec -it nginx-pod bash
```

Puis tester Redis via localhost :
```
apt update && apt install -y redis-tools
redis-cli -h localhost ping
```

Résultat attendu :
```
PONG
```

✅ Les conteneurs communiquent via localhost, car ils partagent le même namespace réseau.

🟦 4) Intégration avec systemd (mode utilisateur)

Podman peut générer des services systemd utilisateur, sans droits root.

🔹 Générer le fichier systemd du pod
```
podman generate systemd --name mon-pod --files --new
```

Un fichier est généré, par exemple :
```
pod-mon-pod.service
```
🔹 Installation du service systemd utilisateur
```
mkdir -p ~/.config/systemd/user
mv pod-mon-pod.service ~/.config/systemd/user/
```
🔹 Recharger systemd utilisateur
```
systemctl --user daemon-reexec
systemctl --user daemon-reload
```
🔹 Activer le service au démarrage de la session
```
systemctl --user enable pod-mon-pod.service
systemctl --user start pod-mon-pod.service
```
🔹 Vérifier l’état du service
```
systemctl --user status pod-mon-pod.service
```

✅ Le pod démarre automatiquement à l’ouverture de la session utilisateur.

🟦 5) Questions de réflexion
❓ Quel est l’avantage de ne pas avoir de daemon root ?
```
Ne pas utiliser de daemon root réduit les risques de sécurité. Un conteneur compromis ne peut pas obtenir les privilèges administrateur du système.
```
❓ Pourquoi les conteneurs dans un pod partagent-ils localhost ?
```
Les conteneurs d’un pod partagent le même namespace réseau, ce qui leur permet de communiquer via localhost, comme des processus sur la même machine.
```
❓ Que signifie “rootless” en termes de sécurité ?
```
Le mode rootless signifie que les conteneurs s’exécutent avec les droits d’un utilisateur normal. Cela limite fortement l’impact d’une faille ou d’une attaque.
```
✅ Conclusion

Ce TP m’a permis de :

- Utiliser Podman sans privilèges root
- Lancer des conteneurs rootless
- Comprendre le fonctionnement des Pods
- Intégrer Podman avec systemd utilisateur
- Comparer Podman à Docker

Podman offre une alternative plus sécurisée à Docker, particulièrement adaptée aux environnements multi-utilisateurs.


### 🧪 TP 5 – LXC : conteneur système
🎯 Objectif

Comprendre la différence entre :

- conteneurs applicatifs (Docker / Podman)

🔹 Installation des paquets nécessaires


- La majorité des options doivent être en enabled
- Les namespaces et cgroups doivent être supportés

🟦 2) Création d’un conteneur Ubuntu


- Distribution : ubuntu


🔹 Lister les conteneurs et leur état
```

```

```
ubuntu-test  RUNNING
```

🔹 Attacher un shell au conteneur
```

```

➡️ Je me retrouve dans le conteneur, avec un shell root.
Le conteneur se comporte comme une machine Linux complète.

🟦 4) Installation d’un service dans le conteneur

👉 Contrairement à Docker, LXC possède :

un système init

systemd

plusieurs services

```

```

```
active (running)
```

🔹 Récupération de l’adresse IP du conteneur

```

```


🔹 Arrêt propre du conteneur
```

```

🔹 Destruction du conteneur
```
sudo lxc-destroy -n ubuntu-test
```

🔹 Vérification finale
```

```

Le conteneur n’existe plus.

🟦 7) Questions de réflexion
❓ Quelle est la différence principale avec un conteneur Docker ?
```
Un conteneur Docker lance généralement un seul processus, alors qu’un conteneur LXC exécute un système Linux complet avec systemd, comme une VM légère.
```

❓ Dans quel cas utiliseriez-vous LXC plutôt que Docker ?
```
LXC est utilisé lorsque l’on souhaite :
- un environnement proche d’une VM
- plusieurs services dans un même conteneur
- une gestion classique avec systemd
Docker est plus adapté aux applications isolées.
```

❓ Le conteneur a-t-il son propre kernel ?
```
Non. Le conteneur LXC partage le kernel de l’hôte, contrairement à une machine virtuelle qui possède son propre kernel.
```

✅ Conclusion

Ce TP m’a permis de :

- Comprendre les différences entre LXC et Docker

LXC se rapproche d’une machine virtuelle légère, tandis que Docker est orienté application.


### 🧪 TP 6 – Application multi-conteneurs avec Load Balancing
🎯 Objectif

Déployer une application Flask avec :
- 3 instances
- Redis partagé
- Nginx en load balancer
- Docker Compose
- Réseaux isolés frontend / backend

📁 1️⃣ Préparer l’arborescence
```
mkdir tp6-loadbalancer
cd tp6-loadbalancer

mkdir app
mkdir nginx
```

🐍 2️⃣ Créer l’application Flask
📄 app/app.py
```
from flask import Flask
import redis
import os

app = Flask(__name__)

redis_host = "redis"
redis_port = 6379

r = redis.Redis(host=redis_host, port=redis_port, decode_responses=True)

@app.route("/")
def index():
    count = r.incr("visits")
    hostname = os.environ.get("HOSTNAME")
    return f"Visites : {count} | Conteneur : {hostname}\n"

@app.route("/health")
def health():
    return "OK", 200
```

📄 app/requirements.txt
```
flask
redis
gunicorn
```

🐳 3️⃣ Dockerfile de l’application
📄 app/Dockerfile
```
FROM python:3.11-slim

# Créer un utilisateur non-root
RUN useradd -m appuser

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

USER appuser

EXPOSE 5000

CMD ["gunicorn", "-w", "2", "-b", "0.0.0.0:5000", "app:app"]
```

✔ Image légère
✔ Utilisateur non-root
✔ Gunicorn (propre en prod)

🌐 4️⃣ Configuration Nginx (Load Balancer)
📄 nginx/nginx.conf
```
events {}

http {
    upstream flask_app {
        server app:5000;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://flask_app;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }
    }
}
```

📌 Docker DNS gère le load balancing automatiquement quand il y a plusieurs replicas.

🧱 5️⃣ docker-compose.yml
📄 docker-compose.yml
```
version: "3.9"

services:
  app:
    build: ./app
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 10s
      retries: 3
    networks:
      - frontend
      - backend
    deploy:
      replicas: 3

  redis:
    image: redis:alpine
    volumes:
      - redis-data:/data
    networks:
      - backend

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    networks:
      - frontend
    depends_on:
      - app

networks:
  frontend:
  backend:
    internal: true

volumes:
  redis-data:
```

▶️ 6️⃣ Lancer l’application
```
docker compose up -d --build
```

Vérifier :
```
docker compose ps
```

Résultat attendu :


✔ Le compteur augmente
✔ Le hostname change → load balancing OK
✔ Redis est partagé

💣 8️⃣ Test de résilience
```

docker compose up -d
```

Puis retester :
```
curl localhost
```

➡️ Le service continue de fonctionner.

🧠 Questions de réflexion (RÉPONSES POUR TON RENDU)
❓ Pourquoi Redis n'est-il accessible que depuis le backend ?
```
👉 Pour des raisons de sécurité :
Redis ne doit jamais être exposé à Internet.
```

```
👉 Nginx redirige automatiquement vers les autres instances disponibles.
```

### 🧪 TP 7 – Kubernetes local avec Minikube
🎯 Objectif

Déployer une application Nginx sur Kubernetes avec :
- Réplication
- Service
- Ingress
- Namespace dédié
- Manipulations (scale, update, rollback)

⚙️ 1️⃣ Préparer le cluster Kubernetes
🔹 Démarrer Minikube
```

```

Vérification :
```
kubectl get nodes
```
🔹 Activer l’Ingress Controller
```
minikube addons enable ingress
```

Vérifier :
```
kubectl get pods -n ingress-nginx
```
🔹 Créer un namespace dédié
```
kubectl create namespace tp-kubernetes
```

Vérifier :
```
kubectl get namespaces
```
📄 2️⃣ Créer le fichier Kubernetes
📁 Créer le fichier
```
nano tp7-web-app.yaml
```
📄 Deployment + Service + Ingress
```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: tp-kubernetes
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "64Mi"
            limits:
              cpu: "200m"
              memory: "128Mi"

---
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: tp-kubernetes
spec:
  type: ClusterIP
  selector:
    app: web-app
  ports:
    - port: 80
      targetPort: 80

---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  namespace: tp-kubernetes
spec:
  rules:
    - host: web.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
```

🚀 3️⃣ Déployer l’application
```
kubectl apply -f tp7-web-app.yaml
```

🔍 Vérifications
Pods
```
kubectl get pods -n tp-kubernetes
```
Tous les objets
```
kubectl get all -n tp-kubernetes
```
Ingress
```
kubectl get ingress -n tp-kubernetes
```
🌐 4️⃣ Accéder à l’application
🔹 Récupérer l’IP Minikube
```
minikube ip
```

Exemple :
```
192.168.49.2
```
🔹 Modifier /etc/hosts
```
sudo nano /etc/hosts
```

Ajouter :
```
192.168.49.2 web.local
```
🔹 Tester
```
curl http://web.local
```
Ou navigateur :
```
http://web.local
```

➡️ Page Nginx par défaut = OK ✅

🔧 5️⃣ Manipulations Kubernetes
🔹 Scale à 5 réplicas
```
kubectl scale deployment web-app --replicas=5 -n tp-kubernetes
```

Vérifier :
```
kubectl get pods -n tp-kubernetes
```
🔹 Mettre à jour l’image (rolling update)
```
kubectl set image deployment/web-app nginx=nginx:1.25 -n tp-kubernetes
```

Suivre le déploiement :
```
kubectl rollout status deployment/web-app -n tp-kubernetes
```
🔹 Voir l’historique
```
kubectl rollout history deployment/web-app -n tp-kubernetes
```
🔹 Rollback
```
kubectl rollout undo deployment/web-app -n tp-kubernetes
```

Vérifier :
```
kubectl rollout status deployment/web-app -n tp-kubernetes
```
🧹 6️⃣ Nettoyage
```
kubectl delete namespace tp-kubernetes
```

➡️ Tout est supprimé proprement.

🧠 Questions de réflexion (RÉPONSES POUR TON RENDU)
❓ Que se passe-t-il si vous supprimez un pod manuellement ?
```
👉 Kubernetes recrée automatiquement un nouveau pod pour respecter le nombre de réplicas.
```
❓ Différence entre Service ClusterIP et NodePort ?
```
ClusterIP : accessible uniquement à l’intérieur du cluster

NodePort : accessible depuis l’extérieur via un port du nœud
```
❓ Pourquoi utiliser labels et selectors ?
```
👉 Pour permettre à Kubernetes de lier dynamiquement les pods aux services, déploiements et autres ressources.
```
